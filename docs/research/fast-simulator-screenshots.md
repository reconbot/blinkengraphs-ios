# Fast Simulator screenshots in CI

Sources read on 2026-11-22: runner-images at [`0e63d4f`](https://github.com/actions/runner-images/tree/0e63d4f9d2c29043b4cf1d2f40d1812a7cde1369) (2026-11-20), GitHub docs at [`d7487f5`](https://github.com/github/docs/tree/d7487f5debb5a5a2a6e65e6f9fa539266f5f8db6), Apple developer documentation and Xcode 26.x release notes, and the source of fastlane, swift-snapshot-testing and the apps named below. Links to repos are pinned to the commit that was read. Web findings that are not the owner's own source or issue thread are marked *secondary*. Our numbers come from `.github/workflows/screenshots.yml` on `macos-latest`.

## First boot and "Data Migration"

- Neither GitHub nor Apple documents the migration. I found no Apple page or runner-images doc that names "Data Migration"; the phrase is `simctl bootstatus` output. *Unconfirmed* beyond logs.
- The image never boots a simulator, so every job's first boot migrates. The macOS build scripts only warm the service with [`simctl list`](https://github.com/actions/runner-images/blob/0e63d4f9d2c29043b4cf1d2f40d1812a7cde1369/images/macos/scripts/build/configure-system.sh#L50-L53), [dedupe devices](https://github.com/actions/runner-images/blob/0e63d4f9d2c29043b4cf1d2f40d1812a7cde1369/images/macos/scripts/build/Configure-Xcode-Simulators.ps1), and [build dyld shared caches](https://github.com/actions/runner-images/blob/0e63d4f9d2c29043b4cf1d2f40d1812a7cde1369/images/macos/scripts/build/Install-Xcode.ps1#L45-L50) for Xcode 26+. No script under `images/macos` runs `simctl boot`. [`configure-xcode.sh`](https://github.com/actions/runner-images/blob/0e63d4f9d2c29043b4cf1d2f40d1812a7cde1369/images/macos/scripts/build/configure-xcode.sh#L15-L29) runs `simctl erase all`, but no template references it at this commit.
- Xcode 26.4 [restored automatic dyld shared cache builds "to improve boot time performance"](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_4-release-notes). Performance degrades while they build, and `simctl runtime dyld_shared_cache update --all` finishes them. The image already runs that command, and a runner-images reporter saw it [exit in 0.3 s](https://github.com/actions/runner-images/issues/15252), so the cache isn't our cost.
- After `bootstatus -b` returns, the device keeps working for minutes. In scowld's notes, PosterBoard's wallpaper prewarm runs [5–12 minutes after boot and takes every CPU on the 3-CPU runner](https://github.com/apoorvdarshan/scowld/blob/4bdaf0181ddffd46d95296884cde55da63f5bd0c/scripts/test-ios.sh#L80-L91). Shortcuts, widgets and Spotlight then [keep 1–2 CPUs busy for another 4–10 minutes](https://github.com/apoorvdarshan/scowld/blob/4bdaf0181ddffd46d95296884cde55da63f5bd0c/scripts/ci/prepare-ios-simulator.sh#L48-L51). Gatefold logged a [1-minute load average of 500–760 for 15+ minutes](https://github.com/ourostack/gatefold/issues/198). Wikipedia builds before it boots because ["a just-booted simulator ... made package resolution and compiling several times slower"](https://github.com/wikimedia/wikipedia-ios/blob/0aea1dc8c8a67b2b22ee4a34c56c5a900b1bbe84/.github/actions/unit-test-scheme/action.yml#L52-L56). That matches our 42 s build becoming 4m41s. It likely also explains our 9 s cold shots against 5.5 s warm ones (inference).
- Runner-images has no issue about first-boot duration as such. Related open threads: [#15252](https://github.com/actions/runner-images/issues/15252) (2026-11-04) quotes `Waiting on Data Migration / LaunchServicesMigrator` 2:44 into a boot on Intel, where a 180 s `bootstatus` budget expired. [#12777](https://github.com/actions/runner-images/issues/12777) covers flaky simulator starts; there the reporter's workaround is to run `simctl` before `xcodebuild`. [#13830](https://github.com/actions/runner-images/issues/13830) (2026-03-20, open) reports `simctl io screenshot` failing on macos-26 with "Timeout waiting for screen surfaces". Maintainers have only acknowledged these.

### Ways to skip or shorten it

- **Cache a device that has booted once.** scowld boots a new device, waits for the prewarm and for idle, and [sets PosterBoard's `KEYNOTE_MODE` so later boots skip the prewarm](https://github.com/apoorvdarshan/scowld/blob/4bdaf0181ddffd46d95296884cde55da63f5bd0c/scripts/ci/prepare-ios-simulator.sh#L53-L69). It then shuts the device down and saves the device folder with `actions/cache`, under a key of image version, Xcode build, runtime build and device type ([key code](https://github.com/apoorvdarshan/scowld/blob/4bdaf0181ddffd46d95296884cde55da63f5bd0c/scripts/ci/ios_simulator.py#L57-L72)). To restore, it moves the folder into `~/Library/Developer/CoreSimulator/Devices` and [kills CoreSimulatorService so the service rereads it](https://github.com/apoorvdarshan/scowld/blob/4bdaf0181ddffd46d95296884cde55da63f5bd0c/scripts/test-ios.sh#L61-L62).
  - The scowld maintainer reports a 0.84–1.04 GB cache, 10–31 s restores and job medians of 22.0 → 13.3 min ([PR #52](https://github.com/apoorvdarshan/scowld/pull/52), 2026-10-22).
  - Gatefold measures a clone of a booted-once device at [about half a new boot](https://github.com/ourostack/gatefold/blob/98d7867f86b5d5f4e9dc28c652cd45a48a363d1d/.github/workflows/warm-sim.yml#L3-L5).
  - The repo cache holds [10 GB by default; entries unused for 7 days are evicted](https://github.com/github/docs/blob/d7487f5debb5a5a2a6e65e6f9fa539266f5f8db6/content/actions/reference/workflows-and-actions/dependency-caching.md). A key that includes `ImageVersion` misses after every image update.
- **Boot with first-boot jobs disabled.** Gatefold passes [`simctl boot --disabledJob=<label>`](https://github.com/ourostack/gatefold/blob/98d7867f86b5d5f4e9dc28c652cd45a48a363d1d/.github/scripts/boot-sim.sh#L91-L107) for [59 launchd labels](https://github.com/ourostack/gatefold/blob/98d7867f86b5d5f4e9dc28c652cd45a48a363d1d/.github/scripts/quiet-sim.labels), among them PosterBoard, photo and media analysis, and search. With them disabled, its probe saw load fall under 25 about 4 minutes after boot, and Settings launches took 0.5–2.5 s. The same probe saw about 18 minutes and launches of up to 351 s with the jobs enabled. Two cautions:
  - Apple publishes no `simctl` reference; `xcrun simctl help boot` on the runner is the primary source, and I couldn't run it here. *Unconfirmed in an Apple source.*
  - [`simctl clone` doesn't keep launchd disables](https://github.com/ourostack/gatefold/issues/198).
- [simslim](https://pkg.go.dev/github.com/mobai-app/simslim@v0.3.0) wraps the same idea (*secondary*; reflect-open uses it).
- No `xcodebuild` setting skips migration that I could find.
- Turning off Spotlight on the host (`sudo mdutil -a -i off`), as [Wikipedia does](https://github.com/wikimedia/wikipedia-ios/blob/0aea1dc8c8a67b2b22ee4a34c56c5a900b1bbe84/.github/actions/prepare-simulator/action.yml#L45-L51), cuts host load. It doesn't touch the simulator's own indexing.

## Per-shot cost

- Apple publishes no figure for `simctl launch` or `terminate`. Our script already prints `timing … terminate= launch= ready= screenshot= resize=` for each shot. Read that split before changing anything.
- *Secondary* reports put a healthy `simctl io screenshot` at [~130–650 ms](https://github.com/lvlrSajjad/simframe), but 10–30 s right after boot or under build load ([waterui#4083](https://github.com/water-rs/waterui/issues/4083), [hozo#2152](https://github.com/iray-tno/hozo/issues/2152)). That again points at first-boot load.

### Options

- **One XCUITest run (fastlane snapshot's approach).** [`snapshot()`](https://github.com/fastlane/fastlane/blob/105fd3c362ef7eb5cc1e36754cbc83115e5d78c0/snapshot/lib/assets/SnapshotHelper.swift#L145-L170) waits up to 20 s for the network indicator to clear, `sleep(1)`s when `waitForAnimations` is on (the default), then saves `XCUIScreen.main.screenshot()`. Apple: [`XCUIScreen.screenshot()`](https://developer.apple.com/documentation/xcuiautomation/xcuiscreen) captures the whole screen, status bar included.
  - fastlane sets dark mode by [writing `UserInterfaceStyleMode` into the device's plist before boot](https://github.com/fastlane/fastlane/blob/105fd3c362ef7eb5cc1e36754cbc83115e5d78c0/snapshot/lib/snapshot/simulator_launchers/simulator_launcher_base.rb#L185-L194), and it [sleeps 10 s after `bootstatus` before the status bar override](https://github.com/fastlane/fastlane/blob/105fd3c362ef7eb5cc1e36754cbc83115e5d78c0/snapshot/lib/snapshot/simulator_launchers/simulator_launcher_base.rb#L118-L130).
  - Relaunching per state saves nothing: [`XCUIApplication.launch()`](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/launch()) "terminates the existing instance" first. XCUITest helps only if the test drives one process through every state by tapping. It also adds a UI-test target to build and a test runner to start.
  - A simslim issue reports [~10 s added to each `XCUIApplication.launch()` when gamed is disabled](https://github.com/MobAI-App/simslim/issues/58). There, plain `simctl launch` had no such stall.
- **In-app rendering.** [`ImageRenderer`](https://developer.apple.com/documentation/swiftui/imagerenderer) leaves out "views whose contents are composited by Core Animation layers, such as more complex controls and containers ... and most types of UIKit and AppKit views", and draws a placeholder instead. Our dashboard is a `ScrollView` in a navigation stack with a toolbar, so this is a poor fit.
  - swift-snapshot-testing renders with [`layer.render(in:)`, or `drawHierarchy(in:afterScreenUpdates:)` when `drawHierarchyInKeyWindow`](https://github.com/pointfreeco/swift-snapshot-testing/blob/0c6380dd46cd45e00f2bf87cf6002f3478e84452/Sources/SnapshotTesting/Common/View.swift#L990-L998). It only simulates safe-area insets, so no status bar is captured.
  - [`drawHierarchy`](https://developer.apple.com/documentation/uikit/uiview/drawhierarchy(in:afterscreenupdates:)) on the key window would capture the navigation bar and scroll content with no host round trip. The status bar belongs to the system, not to our window (inference, not stated by Apple).
- **`simctl io screenshot` with no relaunch.** The app holds one process, steps through the states itself, and handshakes through files in its Documents folder, which is a host path (`get_app_container … data`). This keeps the status bar override and the real window. It removes terminate, launch, app start-up and the scene's first frame from each shot. Two caveats:
  - `.defaultScrollAnchor` applies only when the view appears, so top and bottom positions need `scrollPosition` or a `ScrollViewReader` (inference).
  - State can leak between shots, which a relaunch prevents.
- **Parallel simulators.** fastlane runs concurrent simulators by default, [capped at CPU count − 1](https://github.com/fastlane/fastlane/blob/105fd3c362ef7eb5cc1e36754cbc83115e5d78c0/snapshot/lib/snapshot/simulator_launchers/simulator_launcher.rb#L31-L41). That allows 2 on a 3-CPU runner, and each extra device repeats the first-boot load above.
  - A *secondary* Trendyol post found four parallel simulators [flaky and slow](https://medium.com/trendyol-tech/building-mac-farm-running-2000-ios-pipelines-daily-b3feceea1789).
  - A matrix of separate jobs avoids the contention, but each job pays its own build and boot.
- **Appearance.** `simctl ui <udid> appearance` changes the system setting, so a running app gets a trait change without a relaunch. Our app also sets [`overrideUserInterfaceStyle`](https://developer.apple.com/documentation/uikit/uiview/overrideuserinterfacestyle) on its windows (`App/Sources/BlinkengraphsApp.swift`). Apple: on a `UIWindow` the override "applies to everything in the window". Either works in-process. Whether the status bar text follows a window override is *unconfirmed*; check the light shots.

## What open-source apps do

- **Element X** (element-hq/element-x-ios): swift-snapshot-testing of SwiftUI previews, on an [iPhone SE (3rd generation) simulator the tool creates](https://github.com/element-hq/element-x-ios/blob/1e15227ccffa6f20dc78c9f12e6dbb778477faa9/Tools/Sources/Commands/CI/PreviewTests.swift#L14-L33). The harness [warms each preview through `ImageRenderer`, then snapshots it](https://github.com/element-hq/element-x-ios/blob/1e15227ccffa6f20dc78c9f12e6dbb778477faa9/PreviewTests/Sources/PreviewTests.swift#L58-L71). Images are recorded on the hosted `xcode-27` runner when a maintainer adds a label ([workflow](https://github.com/element-hq/element-x-ios/blob/1e15227ccffa6f20dc78c9f12e6dbb778477faa9/.github/workflows/record-snapshots.yml#L11-L46)). These are component images, not App Store-style screens.
- **Kickstarter** (kickstarter/ios-oss): snapshot tests on CircleCI, not Actions. A [`macos/preboot-simulator`](https://github.com/kickstarter/ios-oss/blob/2c710dec9ec2e96f3739a42078c77c7306d1f066/.circleci/config.yml#L41-L58) step boots before `make test`, and failed snapshots upload as artifacts.
- **Wikipedia**: no screenshot generation (`skip_screenshots: true` in its Fastfile). Its CI shows the boot ordering above, logs `Simulator boot took …s`, and runs on `xcode-27`.
- **Signal, Mastodon, Ice Cubes**: no screenshot step in their workflows at [Signal `4537228`](https://github.com/signalapp/Signal-iOS/tree/45372289a9387cd4271a2f7a47dba8ba92951e41/.github/workflows), [Mastodon `2c165fc`](https://github.com/mastodon/mastodon-ios/blob/2c165fcf91318b2b95643fcdd3c6f2dc3ca8dfd0/fastlane/Fastfile#L86) (`skip_screenshots: true`) and [Ice Cubes `98098b9`](https://github.com/Dimillian/IceCubesApp/tree/98098b9c4b5928f89f338203193c2bf40ab7f38c/.github/workflows).
- I found no first-party engineering post from Airbnb, Uber, Spotify or Lyft on simulator boot speed. The *secondary* posts I found ([Mercadona](https://medium.com/mercadona-tech/reduce-ios-ci-time-using-test-parallelization-de949a80fc5f), [Agoda](https://medium.com/agoda-engineering/how-we-manage-200-mac-minis-for-ios-ci-at-agoda-vitaliy-gorbachov-4e67d7189031)) cover test parallelism on their own Mac fleets.

## Runner choice

- GitHub documents specs, not simulator speed. Standard arm64 runners (`macos-latest`, `macos-15`, `macos-26`, `xcode-27`) have [3 M1 CPUs, 7 GB RAM and 14 GB SSD](https://github.com/github/docs/blob/d7487f5debb5a5a2a6e65e6f9fa539266f5f8db6/data/reusables/actions/supported-github-runners.md). Intel `macos-15-intel` and `macos-26-intel` have 4 CPUs and 14 GB. The `-xlarge` arm64 runner has [5 M2 CPUs "+ 8 GPU hardware acceleration" and 14 GB](https://github.com/github/docs/blob/d7487f5debb5a5a2a6e65e6f9fa539266f5f8db6/data/reusables/actions/larger-runners-table.md). Standard runners are free on public repos. Larger-runner use in public repos ["is also billed at the per-minute rate"](https://github.com/github/docs/blob/d7487f5debb5a5a2a6e65e6f9fa539266f5f8db6/content/actions/concepts/runners/larger-runners.md#billing).
- I found no GitHub or runner-images figure comparing boot or launch speed across macos-15, macos-26, xlarge or Intel. Only reports exist: Intel boots that time out ([#15252](https://github.com/actions/runner-images/issues/15252)), and screenshot timeouts on macos-26 that went away on macos-15 ([#13830](https://github.com/actions/runner-images/issues/13830)).
- `macos-latest` is macOS 26.7.2 arm64 with Xcode 26.6 by default. iPhone 17 Pro exists on the [iOS 26.2, 26.4 and 26.5 runtimes](https://github.com/actions/runner-images/blob/0e63d4f9d2c29043b4cf1d2f40d1812a7cde1369/images/macos/macos-26-arm64-Readme.md#installed-simulators), and Xcode 26.6's SDK is 26.5. Our jq takes the `last` match in dictionary order, which picked 26.2.
- `xcodegen` isn't on the image ([readme](https://github.com/actions/runner-images/blob/0e63d4f9d2c29043b4cf1d2f40d1812a7cde1369/images/macos/macos-26-arm64-Readme.md)), so `brew install` runs on every job. Its time isn't measured.

## Recommendations for our job

Ranked by expected saving on a 7–10 min job. The savings are estimates from the figures above, not measurements.

1. **One launch, the app steps through the states, host captures with `simctl io screenshot`.** Add a `-demo all` sequence that switches scenario, range and scroll position in-process. Use a ready/ack file pair in Documents per shot, and set appearance with `simctl ui appearance` between passes. Saving: 27 × roughly 4–7 s ≈ **2–3 min**. Trade-offs: demo sequencing code in the app, state that can leak between shots, and scroll position driven by code. Confidence: **medium**; check the `timing` split first.
2. **Keep first-boot work off the shots.** Boot with `--disabledJob` for PosterBoard, analysis and search jobs (gatefold's list), so cold shots run at warm speed and fewer screenshots stall. Saving: **~0.5–1.5 min** (cold 9 s against warm 5.5 s per shot), maybe some boot time. Trade-offs: the flag is undocumented by Apple, labels may change with each runtime, and a disabled job the app needs breaks it. Confidence: **low–medium**.
3. **Cache a booted-once, keynote-mode device.** Saving: boot 71 s to an estimated ~35 s, less a 10–30 s restore. That nets **0–40 s**, plus less post-boot load. Trade-offs: ~1 GB of a 10 GB cache, a miss after each image update, and a prepare job to maintain. Confidence: **low** on size, since our boot is already short.
4. **Move `sips` out of the loop** (background it or batch it after capture), and set `HOMEBREW_NO_AUTO_UPDATE=1` for `brew install xcodegen`. Saving: **seconds to tens of seconds**, unmeasured. Trade-off: none. Confidence: **medium** that it helps, **low** on size.
5. **Split dark and light into a two-job matrix.** Saving: **~1–1.5 min** wall time. Each job pays its own ~2 min of build and boot, which is free on a public repo. Trade-off: twice the setup and a merge step for the index. Confidence: **low–medium**. Don't run two simulators on one 3-CPU runner.
6. **Don't adopt:**
   - XCUITest or fastlane snapshot: no gain over item 1, plus a test target and a runner (confidence **medium**).
   - In-app `ImageRenderer`: placeholders for ScrollView and toolbar (**high**).
   - `drawHierarchy` capture: fastest, but loses the status bar (**medium**).
   - `-xlarge` runners: paid per minute, speed-up undocumented (**low**).
